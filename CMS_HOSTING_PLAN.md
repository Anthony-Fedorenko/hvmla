# План: CMS, хостинг и автоматизация контента

> Документ на русском — рабочий язык всего обсуждения, документ внутренний (не для внешних разработчиков).
> Покрывает: переезд с WordPress, выбор CMS для клиента, хостинг/биллинг, автоматизацию стримов (YouTube API), безопасность и секреты, workflow dev → prod.

## Контекст

Приходской сайт (Holy Virgin Mary Russian Orthodox Cathedral) сейчас существует в двух местах:
- **Прод** — WordPress на SiteGround (аккаунт GrowBig).
- **В разработке** — новый сайт на React/Vite, задеплоенный на Vercel.

Цель: полностью заменить WordPress новым сайтом и дать клиенту возможность самому публиковать новости/анонсы/расписание/бюллетени — по аналогии с WordPress («поменял → Publish → на проде»), без участия разработчика. Плюс:
- автоматизировать стримы и архив стримов (сейчас video ID захардкожены в коде);
- сделать всё это безопасно (секреты, доступы, поверхность атаки).

## Почему CMS вообще нужна, и почему git-based

Сейчас весь контент зашит в исходный код:
- Новости/объявления — `src/data/announcements.ts`
- Расписание служб — `src/data/services.ts`
- Бюллетени — массив PDF-ссылок в `src/pages/education/Bulletin.tsx`
- Стримы/архив — захардкоженные YouTube video ID в `LiveStreams.tsx` / `StreamArchive.tsx`

Любое изменение требует правки TypeScript, коммита и пересборки — клиент сам это делать не может.

Рассматривались 3 варианта CMS/бэкенда:
1. **Git-based CMS (Decap CMS)** — выбран. Контент хранится как файлы в репозитории, «Publish» = git-коммит → пересборка → деплой. Нет сервера, нет БД — минимальная поверхность атаки, дёшево.
2. Hosted headless CMS (Sanity/Contentful) — отклонён: платный по мере роста, лишняя внешняя зависимость.
3. Self-hosted CMS+backend (Payload/Strapi + Postgres) — отклонён: нужен постоянно работающий сервер + БД + патчинг, то есть весь security-overhead, от которого и уходим вместе с WordPress.

## Почему не уходим с SiteGround и не переезжаем на другой хостинг

- Email (несколько ящиков на @hvmla-домене) хостится на том же SiteGround-аккаунте — миграция на другой хостинг создаёт реальный риск для почты (MX, простой, потеря писем) без чёткой выгоды.
- Текущий инод-перегруз (в моменте — 71 011 инодов при скромном трафике: ~7 635 уников/мес, ~10 499 просмотров) почти наверняка вызван самим WordPress (core, плагины, кэш, бэкапы, медиатека, ревизии), а не реальной нагрузкой сайта. После полного удаления WP это должно резко упасть.
- Разница между витринной ценой SiteGround и фактическим счётом (клиент платит ~$100/мес при витринной цене тарифа ~$30/мес) — задокументированный паттерн (промо-цена для нового клиента vs renewal-цена, которая может быть в 3-5 раз выше, плюс платные допы). Отдельный биллинговый вопрос, не блокирующий техническую миграцию.

### План по биллингу/тарифу (параллельно, не блокирует миграцию)

1. Доделать техническую миграцию (см. ниже) на текущем GrowBig-аккаунте.
2. Полностью удалить файлы и БД WordPress.
3. Заново посмотреть инody в Site Tools → Statistics.
4. С этой цифрой обратиться в поддержку SiteGround за итемизацией счёта (Billing → Services) и пересмотром тарифа под фактическое использование.
5. Почта при этом не трогается — от тарифа плана не зависит.

## Целевая архитектура

> **Обновление:** у SiteGround в Site Tools появился раздел **Node.js** (деплой Node-приложения из Git + логи) — раньше его не было, поэтому OAuth/YouTube-прокси ниже были заложены на PHP. Теперь оба реализуются на Node.js — один стек JS/TS на весь проект. См. также «Под вопросом: переезд прод-хостинга» ниже — если прод всё же уедет с SiteGround на Vercel/Hostinger, эти прокси переедут туда же (как serverless/edge-функции или отдельный Node-сервис), сама логика не меняется.

- **Прод-хостинг**: SiteGround (GrowBig) — Node.js-хостинг (Site Tools → Node.js) для прокси-скриптов, статика сайта — как обычно через обычный webroot; Git-инструмент в Site Tools для деплоя, доступен SSH.
- **Dev/staging**: Vercel — уже используется для разработки, становится официальной staging-средой (см. раздел ниже).
- **CI/сборка**: GitHub Actions собирает `npm run build` и пушит содержимое `dist/` в отдельную ветку (`production-deploy`) — Git-инструмент SiteGround тянет файлы как есть и не умеет сам запускать build.
- **Деплой на прод**: Git-инструмент SiteGround подключён к ветке `production-deploy` (уточнить на месте: авто-деплой по webhook или по кнопке — см. «Под вопросом» ниже, это же ограничение и есть повод рассмотреть переезд).
- **CMS**: Decap CMS, backend `github` (не `git-gateway` — того нет вне Netlify). Контент — JSON-файлы в репозитории:
  - `content/announcements/*.json`, `content/news/*.json`, `content/schedule.json`, `content/bulletins.json`
  - Decap коммитит изменения через GitHub API.
  - `src/data/*.ts` подхватывает их через `import.meta.glob`, сохраняя текущие интерфейсы (`Announcement`, `ServiceDay`, `NewsItem` и т.п.) — страницы (`Announcements.tsx`, `NewsPage.tsx`, `ServiceSchedule.tsx`, `Bulletin.tsx`) не меняются.
- **OAuth для Decap**: GitHub требует серверного обмена code→token. Реализуем как Node.js-приложение на SiteGround (Site Tools → Node.js, деплой из Git) — либо готовый open-source OAuth-провайдер для Decap (например `@decap-cms/oauth-provider-node` / аналог `netlify-cms-oauth-provider-node`), либо свой минимальный Express-эндпоинт на 2 роута (`/auth`, `/callback`).
- **Стримы/архив**: Node-эндпоинт (тот же Node-процесс, доп. роут `/youtube`) к YouTube Data API v3 по каналу — заменяет захардкоженные video ID в `LiveStreams.tsx` / `StreamArchive.tsx`.

## Секреты и API-ключи

| Секрет | Где используется | Где хранится |
|---|---|---|
| `YOUTUBE_API_KEY` | Node-эндпоинт `/youtube` — запрос live/архива к YouTube Data API v3 | Переменная окружения Node-приложения в Site Tools (не в git) |
| GitHub OAuth Client ID / Secret | Node-эндпоинты `/auth`, `/callback` — логин редактора в Decap CMS | Client ID — публичный (можно в `config.yml`), Secret — переменная окружения Node-приложения (не в git) |

Правила:
- Ничего из вышеперечисленного не коммитится в репозиторий (проверить `.gitignore`).
- Доступ к CMS — только приглашённые GitHub-коллабораторы репозитория (никакой открытой регистрации).
- YouTube API key — ограничить в Google Cloud Console по HTTP-referrer (домен сайта) и/или по IP SiteGround-сервера, чтобы ключ нельзя было переиспользовать при утечке.
- Security-заголовки (CSP, X-Frame-Options, X-Content-Type-Options) — через `.htaccess` (Apache на SiteGround).

## Dev (Vercel) → Prod (SiteGround): защищённый workflow публикации

Да, можно и нужно оставить Vercel как «условный dev/staging», а на прод (SiteGround) катить изменения только вручную, после проверки:

1. **Ветка `main`** — рабочая ветка, куда попадают все изменения (в т.ч. коммиты от Decap CMS). Vercel уже подключён к репозиторию и продолжает автоматически деплоить каждый push в `main` как preview/staging-сайт — это и есть «условный dev». Ничего дополнительно настраивать не нужно, Vercel это уже делает нативно.
2. **Ветка `production-deploy`** — отдельная от `main`. GitHub Actions workflow, который собирает проект и пушит `dist/` в эту ветку, настраивается так, чтобы запускаться **только** при пуше/merge именно в эту ветку, либо по ручному триггеру (`workflow_dispatch`).
3. Site Tools SiteGround смотрит **только** на `production-deploy` — прод обновляется исключительно тогда, когда кто-то явно смёржил/запушил в эту ветку.
4. Процесс публикации: правки/контент через Decap попадают в `main` → сразу видно на Vercel-preview → если всё ок, вручную создаётся PR/merge из `main` в `production-deploy` (или запускается workflow_dispatch) → GitHub Actions собирает и катит на SiteGround.
5. **Доп. страховка (опционально)**: GitHub **Environments** с правилом "required reviewers" для продовского workflow — тогда даже при пуше в `production-deploy` деплой-джоб встанет на паузу и потребует явного "Approve" от заданного человека перед реальным деплоем на SiteGround.

Итого: Vercel = мгновенный dev-предпросмотр любых изменений, SiteGround = прод, обновляется только осознанным действием (merge в отдельную ветку + опционально ручное approve).

## Шаги реализации

1. GitHub Actions workflow: build → push `dist/` в `production-deploy` (триггер — только эта ветка / `workflow_dispatch`).
2. Настроить Git-инструмент в Site Tools SiteGround на ветку `production-deploy`, проверить auto-deploy/webhook.
3. Перенос контента в `content/**/*.json` + рефактор `src/data/announcements.ts` / `services.ts` / `Bulletin.tsx` на `import.meta.glob`.
4. Decap CMS admin (`public/admin/index.html` + `config.yml`, backend `github`).
5. Node.js-приложение на SiteGround (Site Tools → Node.js) с OAuth-прокси для GitHub-логина Decap (`/auth`, `/callback`).
6. Тот же Node-процесс: роут для YouTube Data API (`/youtube`) + обновить `LiveStreams.tsx` / `StreamArchive.tsx`.
7. `.htaccess` с security-заголовками.
8. Настроить GitHub Environment + required reviewers (опционально, доп. ручной гейт перед продом).

## Проверка

- Локально: `npm run dev` + `/admin`, отредактировать тестовую запись, убедиться что коммит ушёл в `main`.
- Vercel: убедиться, что preview обновился с новым контентом.
- Смёржить/запушить в `production-deploy`, проверить что Actions собрал и запушил `dist/`, что SiteGround подтянул изменения, и что они реально появились на живом сайте.
- Проверить Node-эндпоинты: `/youtube` возвращает актуальный live/архив; `/auth` → `/callback` успешно логинит в Decap.

## Под вопросом: возможный переезд прод-хостинга (не решено)

Рассматривается переезд прод-хостинга с SiteGround на **Vercel** или **Hostinger** — основная причина: после того как контент публикуется через Decap CMS (git-коммит), хочется настоящего автодеплоя «коммит → сразу на проде», без ручного шага. Сейчас у SiteGround это под вопросом (см. «Открытые вопросы» ниже — неизвестно, поддерживает ли Git-инструмент на этом аккаунте webhook, или только кнопку вручную).

- **Vercel** — уже используется как dev/staging и по умолчанию деплоит каждый push. Технически прод можно сделать так же: назначить прод-домен на ветку `production-deploy` (Vercel Production Branch), а `main` оставить как preview — тогда почти всё из раздела «Dev → Prod workflow» выше сохраняется, просто без GitHub Actions и без SiteGround Git-инструмента. OAuth- и YouTube-прокси в этом случае становятся Vercel Serverless Functions (`api/auth.ts`, `api/callback.ts`, `api/youtube.ts`) — тоже Node/TS, PHP не нужен вообще.
- **Hostinger** — на части тарифов тоже есть Git-деплой / Node-хостинг, детали и наличие настоящего webhook-автодеплоя не проверялись, нужно уточнять аналогично SiteGround.
- Email на @hvmla остаётся на SiteGround в любом случае (см. «Почему не уходим с SiteGround» выше) — переезд, если состоится, касается только прод-хостинга сайта, не почты.

Пока не решено — план архитектуры выше (SiteGround + Node.js) остаётся рабочим вариантом по умолчанию; если решат переезжать, PHP тут точно не нужен ни при каком раскладе — актуален только выбор Node-раздела на SiteGround vs Serverless-функции на Vercel/Hostinger.

## Портфолио: параллельная AWS-версия (после AWS SAA, не блокирует прод)

Цель — не менять прод, а собрать на тех же исходниках демонстрационную среду на AWS для портфолио (после сдачи AWS Certified Solutions Architect – Associate). Прод остаётся на SiteGround (или Vercel, см. выше): приходу нужен простой и дешёвый сайт, который сможет поддерживать не только автор.

Статика собирается в тот же `dist/`, поэтому AWS-версия не требует правок приложения — только инфраструктура и пайплайн.

### Состав

- **Хостинг**: S3 (приватный бакет) + CloudFront (OAC) + ACM (HTTPS) + Route 53.
- **IaC**: Terraform или CDK — весь стек в отдельном репозитории/директории, без ручных кликов в консоли.
- **CI/CD**: GitHub Actions → AWS через OIDC (без долгоживущих ключей) → `s3 sync` + инвалидация CloudFront.
- **Contact-форма**: API Gateway + Lambda + SES (серверная часть, которой нет на статическом сайте).
- **Legacy QR-ссылки** (`/003-seraphim` и т.п.): CloudFront Function — редирект/rewrite на SPA, вместо catch-all на клиенте там, где это уместно; SPA-fallback (403/404 → `index.html`) для остальных маршрутов.
- **Security-заголовки**: CloudFront Response Headers Policy (аналог `.htaccess` из основного плана).
- **Мониторинг и стоимость**: CloudWatch (алармы, логи Lambda), AWS Budgets-алерт, расчёт месячной стоимости.
- **ADR** (Architecture Decision Record): почему прод остаётся на SiteGround/Vercel, а AWS — демо; сравнение по цене, сложности поддержки, почте, bus factor.

### Что показать в портфолио

- Репозиторий с IaC и README: схема архитектуры, стоимость, как развернуть с нуля одной командой.
- Реальный контекст: двуязычный сайт прихода, миграция с WordPress, QR-ссылки из напечатанного буклета.
- Сравнение двух решений (SiteGround + Node vs AWS) с обоснованием выбора.

### Порядок

1. Сначала довести основной план выше до прода.
2. Сдать AWS SAA (параллельно, в своём темпе).
3. Поднять AWS-версию на отдельном (под)домене или бесплатном CloudFront-домене; прод-домен не трогать.
