# Альтернатива: полный уход с SiteGround на Cloudflare

> Альтернативный вариант к `CMS_HOSTING_PLAN.md`. Тот план оставляет SiteGround как прод-хостинг; этот — убирает его целиком.
> Цели: (1) CMS, простая для священника; (2) бэкенд для секретов; (3) деплой без участия разработчика: **Publish → через пару минут на проде**; (4) снизить расходы (~$35/мес на SiteGround).
> Цены и лимиты Cloudflare/Resend/Google ниже указаны по памяти — перед запуском проверить на их сайтах.

## Что выяснено про текущую инфраструктуру

По публичным данным `hvmla.org` (DNS/RDAP, 2026-10-12):

| Что | Где сейчас |
|---|---|
| Регистратор домена | **Dynadot** (не SiteGround), действует до **2027-02-01** |
| Nameservers (DNS) | SiteGround (`ns1/ns2.siteground.net`) |
| Почта (MX) | **Google Workspace** (`aspmx.l.google.com` и alt1–4) |
| SPF | `include:_spf.google.com` + SiteGround smarthost |
| Сайт (A-запись) | SiteGround |

Дополнительно:
- На SiteGround остался **один почтовый ящик — личный, священника**. Остальные ящики на Google Workspace.
- **Контактная форма сейчас ничего не отправляет**: `handleSubmit` в `src/pages/contact/ContactForm.tsx` только ставит `status = "success"` и очищает поля (комментарий «For demo, we simulate a successful submission»). Если форма уже на проде — посетители не знают, что письма не доходят. Исправляем в рамках этого плана.

Вывод: SiteGround отвечает только за хостинг сайта, DNS и один ящик. Всё это переносится без риска для основной почты. Тезис «почта привязывает к SiteGround» из `CMS_HOSTING_PLAN.md` устарел.

## Целевая архитектура

```
Священник в /admin (Decap CMS) → Publish
        │
        ▼ коммит через GitHub API
GitHub (ветка main)
        │
        ▼ push
Cloudflare Pages: npm run build (VITE_DISABLE_RUSSIAN=true) → деплой на прод (~1–2 мин)

Cloudflare Workers (бэкенд, секреты в Cloudflare):
  /auth, /callback  — GitHub OAuth для Decap
  /api/youtube      — live/архив стримов (YouTube Data API v3, кэш)
  /api/contact      — отправка контактной формы
```

- **Хостинг**: Cloudflare Pages, Production Branch = `main`. Деплой нативный, без GitHub Actions и без ветки `production-deploy`.
- **Превью**: Cloudflare Pages автоматически создаёт preview для остальных веток/PR — отдельный Vercel-staging не нужен (Vercel можно отключить).
- **SPA-маршруты**: Pages отдаёт `index.html` для неизвестных путей (если нет `404.html`), поэтому legacy QR-ссылки (`/003-seraphim` и т.п.) продолжают работать через catch-all `:legacyId` в роутере.
- **DNS**: переносим на Cloudflare (бесплатно). Регистратор остаётся Dynadot, там меняются только nameservers.
- **Почта**: остаётся на Google Workspace, MX не меняются.
- **CMS**: Decap CMS, backend `github`, контент — JSON в `content/**` (как в основном плане; рефактор `src/data/*.ts` на `import.meta.glob` без изменений).
- **OAuth для Decap**: Cloudflare Worker (есть готовые open-source реализации для Decap/Sveltia на Workers — выбрать и проверить актуальность, либо свой минимальный на 2 роута).

## Деплой без вашего участия

1. Священник нажимает Publish в Decap → коммит в `main`.
2. Cloudflare Pages видит push, собирает, выкатывает.
3. Сайт обновлён через 1–2 минуты.

Ручной merge в `production-deploy` и approve **убраны** — они противоречат цели.

Защита от поломок без ручного гейта:
- Если build упал — Pages оставляет прошлую рабочую версию, прод не ломается.
- Перед build — валидация `content/**/*.json` по схеме (скрипт в `npm run build` или `prebuild`), чтобы кривой JSON падал на сборке, а не на проде.
- Опционально: Decap **Editorial Workflow** (черновик → ревью → Publish) — если нужна страховка от случайных публикаций.
- Работа разработчика: правки кода — через feature-ветки и PR; push в `main` = деплой на прод, поэтому в `main` идёт только проверенное. Preview-сборка PR показывает результат до merge.

Откат: в Cloudflare Pages можно в один клик откатиться на предыдущий деплой.

## Контактная форма

Сейчас — заглушка. Целевая реализация:

- Форма шлёт `POST /api/contact` на Worker.
- Worker валидирует поля, защищается от спама (honeypot-поле + Cloudflare Turnstile — бесплатная капча), отправляет письмо через почтовый сервис (Resend или аналог; бесплатного тарифа хватает).
- **Получатель** задаётся секретом `CONTACT_TO`. Рекомендация: **группа Google Workspace** (например, `contact@hvmla.org`) — тогда смена ответственного = правка участников группы, без изменения кода и секретов. Группы обычно не требуют платного места.
- **Отправитель** — адрес на домене, например `noreply@hvmla.org`; в DNS добавляются записи SPF/DKIM выбранного почтового сервиса (это делается в Cloudflare DNS в одном месте). Без этого письма попадут в спам.
- Альтернатива без своего кода: Formspree/FormSubmit — проще, но меньше контроля и хуже для портфолио.

## Секреты

| Секрет | Где используется | Где хранится |
|---|---|---|
| `YOUTUBE_API_KEY` | Worker `/api/youtube` | Secret в Cloudflare Worker (не в git) |
| GitHub OAuth Client Secret | Worker `/auth`, `/callback` | Secret в Cloudflare Worker (не в git); Client ID публичный, в `config.yml` |
| Ключ почтового сервиса | Worker `/api/contact` | Secret в Cloudflare Worker |
| `CONTACT_TO` | Worker `/api/contact` | Переменная Worker |
| Turnstile secret key | Worker `/api/contact` | Secret в Cloudflare Worker |

Правила:
- Ничего из этого не коммитится (проверить `.gitignore`).
- Доступ к CMS — только приглашённые GitHub-коллабораторы репозитория.
- YouTube API key ограничить в Google Cloud Console (по API и, где возможно, по referrer/IP).
- Security-заголовки (CSP, X-Frame-Options, X-Content-Type-Options) — файлом `public/_headers` (Cloudflare Pages) вместо `.htaccess`.

## Стримы и архив

Worker `/api/youtube` запрашивает YouTube Data API v3 по каналу и кэширует ответ (например, на 5 минут через `Cache-Control` / Cache API), чтобы не упираться в квоту. `LiveStreams.tsx` / `StreamArchive.tsx` вместо захардкоженных video ID берут данные из этого эндпоинта.

## Стоимость

| Статья | Было | Станет |
|---|---|---|
| SiteGround | ~$35/мес (≈$420/год) | $0 |
| Cloudflare Pages + Workers + DNS | — | $0 (бесплатный тариф; вашего трафика ~10 тыс. просмотров/мес хватает с запасом) |
| Домен (Dynadot) | ~$15/год | ~$15/год |
| Google Workspace | как сейчас | как сейчас (+ место для ящика священника, если решите переносить как отдельный ящик; алиас/группа — обычно бесплатно) |
| Почтовый сервис для формы | — | $0 (бесплатный тариф) |

Если церковь имеет статус 501(c)(3) — проверить Google for Nonprofits (Workspace бесплатно) — отдельная возможная экономия.

## Порядок миграции (без риска для почты)

1. **Подготовка**: выгрузить DNS-зону из SiteGround (Site Tools → DNS Zone Editor) — сохранить все записи (поддомены, DKIM и пр.).
2. **Ящик священника**: договориться с ним, перенести письма (IMAP-миграция в Workspace) и завести адрес в Workspace как отдельное место или алиас; уточнить, что именно он использует.
3. **Сайт**: подключить репозиторий к Cloudflare Pages, проверить сборку на `*.pages.dev` (EN-only build, QR-маршруты, все страницы).
4. **Бэкенд**: Workers (`/auth`, `/callback`, `/api/youtube`, `/api/contact`), секреты, Turnstile, DNS-записи почтового сервиса.
5. **CMS**: контент в `content/**/*.json`, рефактор `src/data/*`, `public/admin/` + `config.yml`; проверить цепочку Publish → прод на `*.pages.dev`.
6. **DNS**: добавить домен на Cloudflare, **скопировать все записи 1:1** (особенно MX/TXT Google), в Dynadot сменить nameservers на Cloudflare. Проверить почту сразу после переключения (отправка и приём).
7. **Прод-домен**: привязать `hvmla.org` / `www` к Pages, проверить HTTPS.
8. **Наблюдение**: неделя без изменений на SiteGround (на случай забытых записей/ящиков).
9. **Закрыть SiteGround**: сначала сделать полный бэкап (файлы + почта), затем отменить тариф. Удалить WordPress.
10. Проверить автопродление домена в Dynadot (срок до 2027-02-01).

## Риски

- **DNS-переезд**: ошибка в MX/TXT = потеря почты. Митигация: копировать записи 1:1, переключать в спокойное время, иметь выгрузку зоны, TTL заранее снизить.
- **Забытые поддомены/сервисы на SiteGround**: проверить DNS-зону и Site Tools целиком до закрытия.
- **Ящик священника**: потеря старых писем при неаккуратном закрытии. Митигация: IMAP-миграция + бэкап.
- **Зависимость от Cloudflare**: стек статический, `dist/` переносим на любой хостинг; Workers — небольшие, переписываются на другие serverless-платформы.
- **Лимиты и условия бесплатных тарифов** могут измениться — проверить перед запуском.

## Сравнение с `CMS_HOSTING_PLAN.md`

| | Основной план (SiteGround) | Альтернатива (Cloudflare) |
|---|---|---|
| Деплой | Actions → ветка `production-deploy` → SiteGround Git (webhook под вопросом) | push в `main` → Pages, нативно |
| Ручные шаги | merge в `production-deploy` (+ approve) | нет |
| Бэкенд | Node.js на SiteGround | Cloudflare Workers |
| Staging | Vercel | preview-деплои Pages |
| Расходы | ~$35/мес | ~$0 (+ домен) |
| Риск миграции | низкий (почта не трогается) | выше (DNS и ящик священника), но управляем |
| Для портфолио | — | Workers, Turnstile, SPF/DKIM, CI-проверки контента; плюс отдельная AWS-версия (раздел в основном плане) |
